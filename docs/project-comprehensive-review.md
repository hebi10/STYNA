# STYNA 프로젝트 종합 검토

검토일: 2026-08-07

## 1. 결론

현재 프로젝트는 포트폴리오용 패션 커머스 데모로서 기능 범위와 시각적 방향이 상당히 잘 정리되어 있습니다. 상품·이벤트·주문·리뷰·QnA·관리자·Firebase Functions까지 실제 서비스에 가까운 흐름을 갖추었고, Firestore Rules와 서버 검증도 단순 목업 수준을 넘어섰습니다.

다만 출시 전 품질 기준으로 보면 다음 다섯 가지가 우선입니다.

1. 로그인 화면의 데모 계정 처리와 소셜 로그인처럼 보이는 UI 정리
2. 상품 상세 탭·옵션·수량 컨트롤의 접근성 의미와 키보드 동작 보완
3. `alert` 중심 오류 피드백을 인라인 상태·재시도 UI로 통일
4. Functions의 내부 오류 상세 노출 차단 및 CORS 범위 축소
5. Rules Emulator 테스트 실행 환경 고정 및 품질 게이트 복구

P0 수준의 즉시 중단 결함은 확인하지 못했습니다. 기능 기반은 강하지만, 접근성·오류 복구·에셋 전송 정책·관리자 반응형을 보완하면 포트폴리오 완성도와 실제 운영 대응력이 함께 올라갑니다.

| `src` | 508개 |

- 홈, 헤더·푸터, 인증, 상품 목록·검색·상세, 장바구니·체크아웃·주문 완료

- TypeScript 타입체크

실제 브라우저 세션을 열어 여러 뷰포트에서 오버레이·스크린리더·터치 동작을 확인하는 단계는 현재 사용할 수 있는 브라우저 제어 도구가 없어 수행하지 못했습니다. 따라서 브라우저 검증이 필요한 항목은 별도 남은 작업으로 표시했습니다.

## 4. 잘된 점

### 제품·디자인

- 홈 화면이 단순 상품 그리드가 아니라 배너, 카테고리, SELECT, 신상품, FILM, 베스트, 세일, Style Now, 포트폴리오 안내로 구성되어 STYNA의 편집형 브랜드 포지션을 보여줍니다.
- `MainBanner`는 데스크톱·모바일 이미지 분리, 드래그·자동 재생·무한 순환, 포커스·호버 일시 정지, `prefers-reduced-motion`, 충분한 조작 영역을 함께 고려했습니다.
- `StynaFilm`은 동영상 자동 재생을 무음·반복·대체 이미지와 함께 다루고 모션 감소 설정도 반영했습니다.
- 상품 목록, 이벤트 목록, Style Now 페이지는 로딩·오류·빈 결과를 별도 상태로 표현하는 공통 패턴이 있습니다.
- 포트폴리오 데모임을 안내하는 문구가 주문·결제·배송의 실제 운영 범위를 과장하지 않도록 구성되어 있습니다.
- `Button`, `Input`, `AsyncStatePanel`, 공통 토큰 등 재사용 가능한 기반이 있어 화면별 편차를 줄일 수 있는 구조입니다.

### 기능·개발

- 62개 라우트가 상품 탐색부터 주문·마이페이지·관리자까지 하나의 제품 흐름으로 연결됩니다.
- 상품 목록은 URL과 필터·검색·정렬 상태를 동기화하고 커서 기반 추가 조회를 사용합니다.
- 주문 생성은 Functions 트랜잭션에서 상품, 옵션, 재고, 쿠폰, 포인트, 결제 모드와 주문 상태를 검증합니다.
- 이벤트 참여는 정책 확인, 중복 참여 방지, 트랜잭션을 갖추고 있습니다.
- 리뷰 작성은 배송 완료 주문, 상품 일치, 구매 옵션, 중복 리뷰 여부를 서버에서 확인합니다.
- 관리자 인증은 Firebase custom claim과 사용자 문서의 role·status를 함께 요구하고 토큰 폐기 검증도 수행합니다.
- QnA 비밀글은 공개 응답에서 안전한 DTO로 변환하고 비밀번호 원문을 노출하지 않는 구조입니다.
- 챗봇은 입력 길이·대화 이력·Origin·HMAC 기반 제한을 별도로 다룹니다.
- SEO는 robots, sitemap, canonical, 상품·이벤트 메타데이터, JSON-LD까지 구현되어 있습니다.
- 테스트 범위가 넓어 현재 일반 Jest 실행에서 1,475개 테스트가 통과했습니다.

## 5. 우선순위별 개선 항목

### P0 — 현재 확인되지 않음

데이터 손실, 인증 우회, 결제 오작동처럼 즉시 배포를 중단해야 하는 결함은 이번 검토에서 확인하지 못했습니다. 단, Rules Emulator 테스트가 정상 실행되지 않아 Firestore·Storage Rules의 새 변경을 이번 실행에서 재검증하지 못한 점은 품질 게이트의 별도 차단 요소입니다.

### P1 — 배포 전 권장

#### P1-1. 데모 계정과 소셜 로그인 UI의 보안·제품 메시지 정리

위치: `src/app/auth/login/page.tsx`의 데모 로그인 처리부

현재 클라이언트 코드에 데모 계정 처리 로직이 있고, 특정 공개 환경 변수에 따라 노출될 수 있습니다. 또한 UI가 일반 회원·관리자 데모 버튼을 소셜 로그인처럼 보이게 다루는 흔적이 있어 `PRODUCT.md`의 “실제 소셜 OAuth 미사용” 정책과 혼동될 수 있습니다.

영향:

- 공개 번들에서 데모 로그인 정보가 추출될 가능성
- 포트폴리오 관람자가 실제 네이버·카카오 OAuth가 연결되었다고 오해할 가능성
- 데모 계정이 운영 계정 권한과 섞일 경우 권한 확장 위험

권장 조치:

- 데모 계정은 서버 측 시드·환경별 제한·최소 권한 계정으로 분리합니다.
- 클라이언트 소스의 자격 증명 리터럴을 제거하고, 화면에서는 “데모 계정으로 체험”처럼 실제 OAuth와 구분되는 이름을 사용합니다.
- 배포 환경에서는 `NEXT_PUBLIC_ENABLE_DEMO_LOGIN`의 허용 범위와 계정 권한을 체크리스트로 고정합니다.
- 데모 비밀번호를 이미 외부에 공개했던 적이 있다면 회전하고, 실제 운영 계정과 재사용하지 않습니다.

#### P1-2. 상품 상세 탭의 접근성 의미와 키보드 동작 보완

위치: `src/app/products/_components/ProductDetailClient.tsx` 탭 렌더링부, `ProductDetail.module.css` 탭 스타일

현재 탭은 버튼과 패널 전환으로 동작하지만 `tablist`, `tab`, `tabpanel`, `aria-selected`, `aria-controls` 관계가 없습니다. 탭을 보는 사용자는 선택 상태를 시각적으로 확인할 수 있지만, 보조기술 사용자는 구조와 현재 선택 탭을 안정적으로 파악하기 어렵습니다.

권장 조치:

- 탭 목록에 `role="tablist"`, 각 탭에 `role="tab"`와 고유 ID를 부여합니다.
- 선택 탭에 `aria-selected`, 패널에 `role="tabpanel"`, `aria-labelledby`를 연결합니다.
- 좌우 화살표·Home·End 키 이동과 선택 탭 포커스 정책을 정의합니다.
- 패널 내용이 바뀔 때 포커스가 사라지지 않도록 실제 DOM 순서를 확인합니다.

#### P1-3. 상품 옵션·수량 컨트롤의 의미와 조작 영역 보완

위치: `src/app/products/_components/ProductDetailClient.tsx` 옵션·수량 컨트롤

사이즈·색상 선택은 일반 버튼처럼 보이지만 선택 상태를 보조기술에 전달하는 속성이 부족합니다. 수량 증감 버튼도 시각적 기호만으로 의미가 전달될 가능성이 있고, 현재 수량 변화가 읽기 전용 상태로 알려지지 않습니다.

권장 조치:

- 관련 선택을 `fieldset`과 `legend`로 묶습니다.
- 토글형 옵션에는 `aria-pressed` 또는 라디오 그룹 의미를 사용합니다.
- 증감 버튼에 “수량 늘리기”, “수량 줄이기”처럼 구체적인 레이블을 부여합니다.
- 수량 텍스트에 `aria-live="polite"`를 적용하되, 불필요한 중복 읽기를 피합니다.
- 모바일 기준 최소 44px 조작 영역을 확인합니다.

#### P1-4. 오류 피드백을 `alert`에서 복구 가능한 상태 UI로 통일

확인 위치: 체크아웃, 주문 완료, 비밀번호 찾기, 세일·상품 리뷰 등

여러 화면이 `alert()`로 실패를 알리고 있어 사용자는 현재 화면의 어느 필드가 문제인지, 다시 시도할 수 있는지, 입력값이 보존되는지 즉시 알기 어렵습니다. 일부 인라인 오류도 `role="alert"` 또는 `role="status"`가 없어 보조기술이 변화를 안정적으로 전달하지 못할 수 있습니다.

권장 조치:

- 인증·주문·리뷰·문의에 공통 `ErrorState` 또는 `AsyncStatePanel`을 적용합니다.
- 서버 오류, 입력 오류, 권한 오류, 일시적 네트워크 오류를 구분합니다.
- 오류 문구 옆에 재시도·로그인·장바구니로 돌아가기 등 다음 행동을 제공합니다.
- 입력 오류는 해당 필드와 `aria-describedby`로 연결합니다.
- 성공·진행 상태는 `role="status"`, 즉시 주의가 필요한 실패는 `role="alert"`로 구분합니다.
- `window.alert`와 `window.confirm`은 삭제·중요 작업의 최소 확인으로 제한합니다.

#### P1-5. Functions의 내부 오류 상세 응답 차단

위치: `functions/src/index.ts`의 Next 서버 오류 응답, 일부 points/coupon handler의 500 응답

Next 서버 오류 응답에 `String(error)` 또는 예외 메시지 상세를 담는 경로가 있습니다. 이런 값은 내부 경로, Firestore 오류, 서비스 정보가 외부에 노출되는 단서가 될 수 있습니다.

권장 조치:

- 외부 응답은 고정된 오류 코드와 사용자용 메시지만 반환합니다.
- 상세 예외는 Functions 로그에 correlation ID와 함께 기록합니다.
- 프로덕션에서만 상세 메시지를 차단하는 분기보다, 기본 동작 자체를 안전한 응답으로 둡니다.
- 클라이언트는 오류 코드별 안내와 재시도 버튼을 사용합니다.

#### P1-6. Rules Emulator 테스트 실행 환경 고정

이번 실행에서는 Rules 테스트가 assertion 실패가 아니라 emulator hub 연결 실패로 중단되었습니다. 첫 실행은 emulator 프로세스 잔류 이후 예기치 않은 오류가 발생했고, 정리 후 재실행에서는 hub가 4400에서 4401로 이동한 뒤 테스트가 4401에 연결되지 못했습니다.

권장 조치:

- `firebase.rules-test.json`, Firebase CLI, emulator suite의 hub 포트를 하나의 명시적 설정으로 고정합니다.
- 기존 emulator 프로세스가 있을 때 포트를 자동 변경하지 않고 사전 점검에서 명확히 실패하게 합니다.
- 규칙 테스트 시작 전에 Firestore·Storage·hub health check를 수행합니다.
- CI에서는 프로젝트별 `projectId`, 포트, 임시 데이터 디렉터리를 분리합니다.
- 정상 환경에서 Firestore Rules와 Storage Rules의 통과 결과를 `quality-gates.md`에 갱신합니다.

### P2 — 다음 개선 주기

#### P2-1. 이미지 캐시 정책을 실제 전달 경로와 일치시키기

관련 위치: `middleware.ts`, `firebase.json`, `next.config.ts`, `public` 에셋 전달 정책

Middleware에는 Firebase Storage URL을 위한 캐시 분기가 있지만 외부 Storage URL은 일반적으로 Next 앱 Middleware를 통과하지 않습니다. 반면 Firebase Hosting 설정에는 `_next/static`·폰트·favicon 헤더가 중심이고 `public` 이미지의 장기 캐시 정책이 충분히 명시되어 있지 않습니다.

또한 `next.config.ts`에서 `images.unoptimized`가 켜져 있어 이미지 리사이징·포맷 최적화 이점을 사용하지 못합니다.

권장 조치:

- 실제 브라우저 Network 경로를 기준으로 Firebase Hosting, Storage CDN, Next Image 중 하나를 이미지 전달 기준으로 정합니다.

삭제는 승인 없이 수행하지 않고 다음 중 하나로 정리하는 것이 안전합니다.

- 원본 디렉터리를 빌드·배포 제외 목록으로 명시
- 파일명과 접근 정책을 문서화하고 공개가 의도된 경우에만 유지

#### P2-3. 리뷰 UI의 레거시 CSS 정리

위치: `src/app/products/_components/ProductReviews.module.css`

이 파일에는 하드코딩 색상, 중복 `.rating`, 모바일 규칙 부족, 작은 입력·버튼, `justify-content: between`처럼 유효하지 않은 선언이 섞여 있습니다. 리뷰 작성 UI는 구매 후 신뢰 형성에 직접 영향을 주므로 공통 디자인 토큰과 상태 패턴으로 옮길 우선순위가 높습니다.

- 별점은 장식용 아이콘과 텍스트 평점 정보를 분리합니다.

#### P2-4. 관리자 모바일 메뉴 접근성 보완

위치: `src/app/admin/AdminShell.tsx`, `src/app/admin/layout.module.css`

관리자 셸의 모바일 메뉴 버튼에 `aria-expanded`·`aria-controls`가 부족하고, 메뉴가 닫힌 상태에서도 변환된 사이드바 내부 포커스가 남을 가능성을 점검해야 합니다. 고객용 헤더에는 Escape·포커스 트랩·배경 inert 처리 등 더 성숙한 패턴이 있으므로 이를 관리자에도 공통화하는 편이 좋습니다.

추가로 관리자 CSS의 `[class*="Card"]`, `[class*="Button"]`, `[class*="Title"]` 같은 광범위 선택자는 클래스 이름이 우연히 일치하는 컴포넌트까지 영향을 받을 수 있습니다. 명시적 공통 클래스 또는 관리자 전용 CSS 모듈로 범위를 좁히는 것이 안전합니다.

#### P2-5. 홈·추천·세일 화면의 초기 전송량과 조회량 조정

홈은 편집형 콘텐츠가 풍부한 대신 첫 화면부터 여러 상품 섹션과 동영상·이미지를 함께 준비합니다. 추천은 큰 상품 목록을 가져온 뒤 일부를 자르고, 세일도 큰 목록을 조회하는 흐름이 있어 데이터와 이미지 전송량이 커질 수 있습니다.

권장 조치:

- 첫 viewport 이후 섹션은 실제 사용자 노출 시점에 맞춘 지연 로딩을 검토합니다.
- 추천·세일 쿼리에 서버 측 limit·정렬·페이지네이션을 적용합니다.
- FILM 비활성 영상의 `preload="auto"`를 필요한 경우에만 사용하고, 모바일 데이터 절약 정책을 검토합니다.
- 이미지 로딩·동영상 로딩·Firestore 조회량을 브라우저와 Firebase 콘솔에서 측정해 우선순위를 정합니다.

#### P2-6. Functions의 공개 API 경계와 배치 작업 안정성 강화

여러 `onRequest` handler가 `cors: true`로 넓게 열려 있습니다. 인증이 내부에 있더라도 알려진 프론트엔드 Origin으로 제한하면 오용과 운영 실수를 줄일 수 있습니다.

쿠폰·포인트 영역에는 다음 운영 리스크도 있습니다.

- 사용자 입력 limit에 상한이 명확하지 않은 경로
- 만료 쿠폰 정리에서 마스터 문서 조회가 반복되는 N+1 구조
- 하나의 Firestore batch에 작업이 몰릴 수 있는 정리 함수

권장 조치:

- 허용 Origin 목록을 환경별로 관리합니다.
- limit을 서버에서 clamp하고 페이지네이션을 사용합니다.
- 배치 작업은 500개 제한과 재시도·부분 실패를 고려해 chunking합니다.
- 반복 읽기는 문서 구조나 일괄 조회로 줄이고 작업량·실행 시간을 모니터링합니다.

#### P2-7. 관리자 오류 화면의 stack 노출 차단

위치: `src/app/admin/_components/ErrorBoundary.tsx`

관리자 오류 화면에서 `error.stack`을 직접 보여주는 경로가 있습니다. 관리자 전용이라도 내부 경로와 구현 세부 정보가 노출될 필요는 없습니다.

권장 조치:

- 사용자 화면에는 오류 ID와 재시도·새로고침 안내만 보여줍니다.
- stack은 서버 로그 또는 개발 환경에서만 확인합니다.
- 관리자 권한이 있더라도 브라우저 화면에 민감한 내부 정보를 기본 노출하지 않습니다.

#### P2-8. QnA 공개 조회의 페이지 확장성 명시

현재 공개 QnA API는 계약상 1페이지 조회 후 클라이언트에서 최대 50개 범위로 검색합니다. 현재 데이터 규모에서는 단순하지만, 문의가 늘면 오래된 항목 검색이 누락됩니다.

권장 조치:

- 서버 페이지네이션·cursor를 도입하거나, 검색용 정규화 필드를 별도로 둡니다.
- “최근 문의 일부만 검색”이 제품 정책이라면 화면에 범위를 안내합니다.
- 로딩·오류 메시지에 `role`을 부여하고 검색 입력의 명시적 레이블을 보완합니다.

#### P2-9. 디자인 토큰과 레거시 스타일의 단일화

현재 CSS에는 약 2,176개의 직접 hex 색상 토큰, 다수의 border-radius·box-shadow 선언, 800 이상의 font-weight 선언, 레거시 화면의 별도 규칙이 함께 존재합니다. 새 화면의 편집형 톤과 기존 인증·지원·관리자 화면의 스타일이 완전히 같은 계층을 사용하지 않습니다.

권장 조치:

- 새 UI부터 의미 기반 토큰을 사용하고 직접 색상·그림자 값을 줄입니다.
- `font-weight: 800`을 500·600·700 체계로 조정합니다.
- 공통 버튼·입력·상태·카드의 변형을 정의해 화면별 재정의를 줄입니다.
- 일괄 치환보다 화면 단위로 시각 회귀를 확인합니다.

## 6. 영역별 상세 피드백

### 6.1 홈·브랜드 경험

강점은 “상품을 많이 보여주는 쇼핑몰”이 아니라 “스타일을 편집해 제안하는 브랜드”라는 방향이 화면 구조에 드러난다는 점입니다. 배너와 Style Now, FILM, SELECT가 서로 다른 콘텐츠 리듬을 만들고, 포트폴리오 안내도 실제 쇼핑 경험을 방해하지 않는 범위에 있습니다.

개선 포인트는 첫 진입 시 선택지가 너무 많아질 수 있다는 점입니다. 특히 모바일에서 홈 전체가 길어지면 상품 탐색 목적의 사용자가 핵심 CTA를 찾기 어렵습니다. 다음을 측정해 조정하는 것이 좋습니다.

- 첫 화면에서 상품 목록으로 이동하는 비율
- 배너 이후 첫 상품 섹션까지의 이탈률
- FILM·Style Now 노출 전후의 이미지·동영상 로딩 시간
- 포트폴리오 안내의 클릭률과 쇼핑 흐름 방해 여부

현재 코드에 시각적으로 숨겨진 H1은 있으므로 SEO 구조는 기본적으로 안전합니다. 다만 콘텐츠가 많아질수록 섹션별 heading 계층과 “본문으로 건너뛰기” 링크를 보완하면 키보드·스크린리더 사용성이 좋아집니다.

### 6.2 헤더·내비게이션

고객용 헤더의 모바일 메뉴는 이번 검토에서 가장 잘 구현된 접근성 패턴 중 하나입니다. Escape 닫기, 포커스 이동, body 스크롤 잠금, 배경 `inert`, route 변경 시 닫기까지 갖추고 있습니다.

남은 과제는 다음입니다.

- skip link 제공
- `Primary`, `Quick links` 같은 접근성 레이블의 제품 언어 통일
- 모바일 메뉴 transition에 reduced-motion 대응 추가
- 960–1279px에서 로고·검색·유틸리티가 밀리지 않는지 브라우저 확인
- 관리자 셸과 고객 헤더의 메뉴 접근성 패턴 공통화

### 6.3 인증·회원

회원가입은 입력 검증, 첫 오류 포커스, `aria-describedby`, 비밀번호 확인 등 기본 흐름이 탄탄합니다. 로그인도 redirect 검증과 역할별 메시지를 갖추었습니다.

반면 성공·실패를 native alert에 의존하는 화면이 있고, 데모 계정 처리와 실제 인증 기능의 경계가 UI에서 더 명확해야 합니다. 포트폴리오 관람자는 “실제 회원가입인지”, “실제 소셜 로그인인지”, “데모 데이터인지”를 한 번에 이해해야 하므로 인증 화면 상단에 짧은 정책 문구를 고정하는 것이 좋습니다.

### 6.4 상품 탐색·상세·리뷰

상품 목록과 검색은 URL 기반 상태, 필터, 정렬, cursor, 로딩·오류·빈 결과가 잘 연결되어 있습니다. 상품 상세는 정보량이 많지만 가격·옵션·장바구니·리뷰·추천의 상업적 흐름이 자연스럽습니다.

가장 큰 개선점은 상세의 탭·옵션·수량 의미입니다. 이 부분은 시각 스타일보다 사용자가 실제로 “무엇을 선택했는지”와 “어떤 정보가 열려 있는지”를 모든 입력 방식에서 이해할 수 있게 만드는 것이 우선입니다.

리뷰에는 구매 검증 서버 로직이 있어 신뢰 기반은 좋습니다. 이후 이미지 업로드를 추가할 때는 Storage Rules, 파일 크기·타입, EXIF·개인정보, 삭제·수정 정책까지 함께 설계해야 합니다.

### 6.5 장바구니·체크아웃·주문

주문 서버화와 트랜잭션 검증은 프로젝트의 기술적 강점입니다. 데모 결제·배송이라는 경계를 문서와 화면에서 반복적으로 안내하는 것도 포트폴리오 목적에 적합합니다.

개선할 부분은 실패 복구입니다. sessionStorage 기반 초안은 새로고침 보존에는 유용하지만 탭 간 동기화·개인 브라우징·예상치 못한 종료에 한계가 있습니다. 주문 실패 시 입력한 배송지·쿠폰·포인트 선택이 정확히 보존되는지, 다시 시도할 때 중복 주문이 생기지 않는지 브라우저 수동 검증이 필요합니다.

장바구니의 optimistic update는 Firebase 업데이트 실패 시 로컬 화면과 서버 상태가 어긋날 가능성이 있으므로 실패 시 원상 복구하거나 서버 재조회하는 패턴을 명시하는 것이 안전합니다.

### 6.6 이벤트·Style Now·콘텐츠

이벤트 목록은 공개 정책, 상태, 필터, 로딩·빈 결과를 비교적 잘 구분합니다. `picture` 기반 반응형 이미지와 에디토리얼 이미지 품질도 좋습니다.

다만 이미지에 텍스트가 많이 포함된 경우 다음을 점검해야 합니다.

- 작은 화면에서 텍스트가 잘리지 않는지
- 이미지가 로드되지 않아도 핵심 CTA와 기간이 전달되는지
- alt가 이미지 내 문구를 대체해야 하는지, 장식으로 취급해야 하는지
- 한국어·영어 카피가 화면과 메타데이터에서 일치하는지

### 6.7 관리자

관리자는 상품·주문·사용자·이벤트·QnA·리뷰를 실제 운영 콘솔처럼 나누고, 화면에 “아직 서버 API가 없어 비활성화된 작업”을 정직하게 표시합니다. 이는 구현되지 않은 기능을 가능한 것처럼 보이지 않게 하는 좋은 선택입니다.

관리자 전용 CSS의 전역에 가까운 substring selector와 오류 stack 노출은 유지보수·보안 측면에서 우선 정리할 가치가 있습니다. 관리자 모바일 메뉴는 고객용 헤더보다 접근성 상태가 약하므로 공통 Drawer 패턴으로 맞추는 것이 효율적입니다.

### 6.8 보안·데이터·서버

Firestore Rules는 활성 계정, 소유자, 관리자 claim과 문서 role을 함께 확인하고, 주문·리뷰·참여 데이터의 클라이언트 직접 쓰기를 제한합니다. Storage Rules도 파일 타입·크기·경로별 접근 범위를 구분합니다. 이는 단순 프론트엔드 데모보다 훨씬 신뢰할 수 있는 기반입니다.

남은 위험은 “보호되고 있는가”보다 “실패할 때 얼마나 적게 말하는가”와 “공개 API 경계가 얼마나 좁은가”에 가깝습니다. CORS를 제한하고, 예외 상세를 고정 메시지로 바꾸고, 정리 함수의 batch·N+1을 개선하면 운영 안전성이 올라갑니다.

### 6.9 SEO·배포·성능

robots, sitemap, canonical, 상품·이벤트 메타데이터, JSON-LD는 좋은 출발점입니다. JSON-LD 직렬화 시 `<`를 이스케이프하는 처리도 안전한 편입니다.

반면 `images.unoptimized`, 넓은 remote pattern, public 에셋 캐시 헤더, 외부 Storage 캐시 분기의 실제 적용 여부가 서로 완전히 맞물리지 않습니다. 성능 개선은 감으로 일괄 수정하기보다 다음 측정 순서가 적합합니다.

1. 실제 배포 URL에서 첫 화면 이미지·동영상 요청 확인
2. 4G 모바일에서 LCP·INP·CLS 측정
3. Firebase 읽기 수와 Functions 실행 시간 확인
4. 가장 큰 파일과 가장 늦은 섹션부터 최적화

### 6.10 문서·품질 운영

문서 수가 많고 디자인·보안·성능·정책·작업 계획을 분리해 기록한 점은 강점입니다. `docs/README.md`가 현재 코드와 과거 계획 문서의 우선순위를 구분하는 것도 좋습니다.

다만 작업 문서가 많아질수록 “현재 기준 문서”와 “당시 계획”의 차이를 한눈에 보여주는 상태 표가 필요합니다. 특히 `quality-gates.md`의 테스트 수·실행 결과는 현재 검증 결과와 맞춰야 합니다.

### 주의해서 해석할 결과

- `npm run build`는 `next.config.ts`의 `eslint.ignoreDuringBuilds: true` 때문에 빌드 내부 lint를 건너뜁니다. 별도 lint 명령은 통과했으므로 현재 정적 검사 결과와 빌드 설정을 함께 유지해야 합니다.
- UI 감지기의 운영 코드 후보는 대부분 둥근 요소의 강조 border 패턴이며, 로딩 스피너·의도된 상태 표시처럼 실제 결함이 아닐 수 있습니다. 모든 항목을 수동 분류해야 합니다.

### 이번 실행에서 검증하지 못함

- `npm run test:rules` — assertion 결과가 나오기 전에 Firebase Emulator hub가 4400에서 4401로 이동했고, 4401 연결이 거부되어 Firestore·Storage 규칙 테스트가 실행되지 않았습니다. 동일한 개발 환경의 다른 Firebase 프로젝트 emulator는 건드리지 않았습니다.
- 실제 브라우저 뷰포트·키보드·터치·스크린리더 검증 — 브라우저 제어 도구를 사용할 수 없어 수행하지 못했습니다.
