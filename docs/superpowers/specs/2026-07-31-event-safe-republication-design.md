# 이벤트 안전 재공개 및 신규 이벤트 확장 설계

## 배경

Firestore `events` 컬렉션에는 기존 이벤트 22개가 남아 있지만, 모든 문서가 공개 정책 검증을 완료하지 않아 `/events/`에는 0개로 표시된다. 기존 문서에는 자동 쿠폰 지급, 추가 적립금, 생일 쿠폰, 상담 쿠폰, 무료배송과 할인율 보장처럼 현재 데모가 실제로 제공하지 않는 문구가 포함되어 있다.

기존 이벤트와 이미지 중 안전하게 재사용할 수 있는 자산은 보존하고, 구현되지 않은 혜택만 제거한다. 동시에 신규 이벤트 10개를 추가하고, 목록을 `진행·예정 이벤트`와 `종료된 이벤트`로 분리한다.

## 목표

- 기존 이벤트 22개를 삭제하지 않고 검증 가능한 콘텐츠로 재공개한다.
- 신규 이벤트 10개를 실제 상품과 현재 구현된 참여 계약에 맞춰 추가한다.
- 진행·예정 이벤트와 종료 이벤트를 명확히 분리한다.
- 기존 이미지 44개는 시각 검수 후 안전한 자산을 우선 재사용한다.
- Firestore 변경 전 백업과 검증 가능한 적용·복구 경로를 제공한다.
- 운영 데이터와 코드가 서로 다른 상태로 먼저 노출되지 않도록 공개 순서를 통제한다.

## 비목표

- 실제 결제, 자동 할인, 자동 무료배송, 추가 적립금 또는 신규 쿠폰 정책을 구현하지 않는다.
- 기존 Firestore 이벤트 문서나 Storage 객체를 삭제하지 않는다.
- 기존 이미지 파일을 같은 경로에 덮어쓰지 않는다.
- 이벤트 참여 API와 주문·리뷰 증거 판정 구조를 변경하지 않는다.
- 사용자 승인 없이 커밋, 푸시 또는 배포하지 않는다.

## 이벤트 구성

### 기존 이벤트 22개

- 문서 ID와 기존 기간은 유지한다.
- 종료 여부는 `endDate`와 현재 시각을 기준으로 계산한다.
- 공개 가능한 문구와 이미지는 재사용한다.
- 구현되지 않은 혜택 문구는 실제 지원 범위의 안내 문구로 교체한다.
- 종료 이벤트는 상세 조회가 가능하지만 참여 CTA는 비활성화한다.
- 종료된 리뷰 이벤트는 과거 리뷰 안내 콘텐츠로 보존하며 금전성 보상을 약속하지 않는다.

### 신규 이벤트 10개

- 세일형 3개
- 신상품형 3개
- 시즌 기획전형 2개
- 구매 인증 리뷰형 2개

세일형은 고정 할인율이나 자동 할인을 약속하지 않고 `상품별 할인가 확인`을 기준 문구로 사용한다. 신상품형과 시즌 기획전형은 실제 활성 상품을 연결하는 탐색형 콘텐츠로 구성한다. 리뷰형은 실제 활성 상품 문서 ID를 `targetProducts`에 지정하고 `eligibilityType: review`, `rewardType: none`을 사용한다.

신규 이벤트는 다음 구성으로 고정한다. 날짜는 KST의 해당 날짜 00:00부터 종료일 23:59:59까지로 저장한다.

| 유형 | 문서 ID | 제목 | 기간 | 상품 연결 |
| --- | --- | --- | --- | --- |
| 세일 | `event-2026-08-summer-sale-edit` | 라스트 서머 세일 셀렉션 | 2026-08-01~2026-08-23 | `tops`, `bottoms` 세일 상품 |
| 세일 | `event-2026-08-bag-accessory-sale` | 데일리 백 & 액세서리 세일 | 2026-08-08~2026-09-06 | `bags`, `accessories` 세일 상품 |
| 세일 | `event-2026-09-active-sale` | 액티브 라이프 세일 | 2026-09-01~2026-09-30 | `sports`, `shoes` 세일 상품 |
| 신상품 | `event-2026-08-prefall-layering-new` | 프리폴 레이어링 신상 | 2026-08-01~2026-08-31 | `clothing`, `tops` 신상품 |
| 신상품 | `event-2026-08-daily-bag-new` | 데일리 백 신상품 | 2026-08-15~2026-09-15 | `bags` 신상품 |
| 신상품 | `event-2026-09-city-shoes-new` | 시티 슈즈 신상품 | 2026-09-01~2026-09-30 | `shoes` 신상품 |
| 시즌 기획전 | `event-2026-08-late-summer-style` | 늦여름 데일리 리셋 | 2026-08-05~2026-08-31 | `tops`, `bottoms`, `bags` 추천 상품 |
| 시즌 기획전 | `event-2026-09-back-to-city` | 가을 출근룩 큐레이션 | 2026-08-24~2026-09-30 | `clothing`, `bottoms`, `bags`, `shoes` 추천 상품 |
| 구매 인증 리뷰 | `event-2026-08-summer-fit-review` | 여름 소재 구매 인증 리뷰 | 2026-08-01~2026-08-31 | `cool-touch-oversized-shirt`, `linen-like-half-shirt`, `seersucker-half-jacket` |
| 구매 인증 리뷰 | `event-2026-09-prefall-fit-review` | 프리폴 착용 구매 인증 리뷰 | 2026-09-01~2026-09-30 | `light-zip-up-jacket`, `style-now-autumn-01`, `style-now-autumn-08` |

위 리뷰 대상 상품 6개는 2026-07-31 읽기 전용 점검에서 모두 `status: active`임을 확인했다. apply와 verify 단계에서도 다시 확인하며, 비활성 또는 누락 상품이 있으면 Firestore 반영을 중단한다. 신규 문서 ID는 재실행해도 중복 문서가 생기지 않는 고정 ID로 사용한다.

## 공개 상태 모델

### 목록 탭

- 기본 탭: `진행·예정 이벤트`
  - `ongoing`과 `upcoming` 이벤트를 함께 표시한다.
- 보조 탭: `종료된 이벤트`
  - `ended` 이벤트를 표시한다.

`isActive`는 공개 가능한 문서인지 나타내는 운영 플래그로 유지한다. 날짜 기반 `ongoing`, `upcoming`, `ended` 상태와 혼용하지 않는다. 공개되는 32개 문서는 `isActive: true`를 유지하고, 종료 여부는 날짜로 구분한다.

### 유형 필터

기존 유형 필터 `전체`, `세일`, `쿠폰`, `특별 이벤트`, `신상품`은 각 상태 탭 안에서 동작한다. 상태 탭이나 유형 필터가 변경되면 페이지를 1로 초기화한다. 페이지네이션은 필터링된 결과를 기준으로 계산한다.

### 상세 및 참여

- 진행 이벤트는 기존 참여 자격과 기간 검사를 사용한다.
- 예정 이벤트는 상세를 볼 수 있지만 참여는 시작 전 상태로 차단한다.
- 종료 이벤트는 상세를 볼 수 있지만 참여는 종료 상태로 차단한다.
- 종료 이벤트의 CTA는 상품 탐색 또는 전체 이벤트 이동 같은 읽기 전용 행동만 제공한다.

## 콘텐츠 검증 기준

### 허용

- 실제 상품 조회와 상품별 가격 확인
- 가입 완료 시 현재 구현된 5,000P
- 주문별 배송 상태 확인
- 실제 주문·배송·구매 인증 리뷰에 기반한 참여 조건
- 보상 없는 상품 탐색·리뷰 안내·시즌 기획전
- 포트폴리오 데모임을 명확히 하는 문구

### 제거 또는 교체

- 자동 쿠폰 지급과 실제로 존재하지 않는 쿠폰 코드
- 추가 적립금, 적립금 배수, 베스트 리뷰 현금성 보상
- 생일 쿠폰, 첫 구매 무료배송, 임의의 무료배송 기준
- 실시간 상담, 상담 전용 쿠폰, 관리자 확인 후 지급 약속
- 상품 데이터로 확인되지 않은 최대 할인율
- 자동 할인·자동 적용·조기 출고 등 구현되지 않은 동작

### 이미지

현재 Firestore에 연결된 기존 배너·카드 이미지 44개를 임시 작업 폴더로 내려받아 접촉 시트를 만든다. 다음 조건을 모두 만족하면 기존 URL을 유지한다.

- 허위 쿠폰·적립·무료배송·상담 문구가 없다.
- 한글이 깨지지 않았다.
- 타사 로고, 워터마크 또는 가짜 브랜드가 없다.
- 이벤트 제목과 안전한 안내 문구가 현재 Firestore 문구와 충돌하지 않는다.
- 목록과 상세에서 주요 피사체가 과도하게 잘리지 않는다.

검수에 실패한 기존 이미지와 신규 이벤트 이미지는 이미지 생성 기능으로 새로 만든다. 신규 객체는 버전이 포함된 새 Storage 경로에 업로드하며 기존 객체를 덮어쓰지 않는다. 신규 이벤트는 최소한 와이드 이미지와 카드 이미지를 각각 가진다. 상세 이미지는 안전한 와이드 이미지를 재사용할 수 있다.

## 데이터 계약

### 공통 필수 필드

- `title`, `description`, `content`
- `eventType`
- `eligibilityType`
- `rewardType`
- `publicPolicyVerified`
- `startDate`, `endDate`
- `isActive`
- `bannerImage`, `thumbnailImage`
- `participantCount`, `hasMaxParticipants`
- `createdAt`, `updatedAt`

### 참여 자격

- 탐색형·종료 이벤트: `eligibilityType: none`, `targetProducts` 필드 없음
- 신규 리뷰 이벤트: `eligibilityType: review`, 유효한 활성 상품 ID 1개 이상

### 보상

- 이번 작업의 32개 이벤트는 `rewardType: none`을 기본값으로 사용한다.
- `rewardCouponId`는 남기지 않는다.
- 새로운 쿠폰 발급 정책은 추가하지 않는다.

### 공개 검증

Firestore 반영용 데이터는 먼저 `publicPolicyVerified: false` 상태로 준비한다. 스키마, 문구, 이미지, 대상 상품, 목록·상세 동작과 배포 상태를 모두 확인한 뒤 최종 공개 단계에서만 32개 문서를 `true`로 전환한다.

## 구현 구조

### UI

- `EventProvider`
  - 전체 공개 이벤트를 보유한다.
  - 유형 필터와 페이지 상태는 기존 구조를 유지한다.
- `EventList`
  - 날짜 상태 탭을 소유한다.
  - 상태 탭과 유형 필터를 조합해 현재 결과를 계산한다.
  - 탭별 이벤트 수와 빈 상태를 표시한다.
- `eventProductSelection`
  - 세일 이벤트의 카테고리 결과는 `isSale: true` 상품만 사용한다.
  - 신상품 이벤트의 카테고리 결과는 `isNew: true` 상품만 사용한다.
  - 시즌 기획전은 카테고리의 활성 상품을 사용한다.
  - 카테고리 결과가 부족하면 기존 유형별 fallback으로 나머지를 채운다.
- 이벤트 상세
  - 기존 `getEventStatus()`와 참여 차단 로직을 재사용한다.
  - 종료 상태에서 참여형 CTA를 표시하지 않는다.

### 데이터 manifest

기존 22개 패치와 신규 10개 문서를 하나의 버전 관리된 manifest로 정의한다. manifest에는 문구, 유형, 기간, 참여 자격, 보상, 대상 상품, 이미지 역할과 공개 검증 기대값을 포함한다.

manifest 검증기는 다음을 확인한다.

- 이벤트 ID 32개가 고유하다.
- 기존 22개 ID가 빠지지 않았다.
- 신규 ID 10개가 중복되지 않는다.
- 금지 문구가 없다.
- 날짜가 유효하고 시작일이 종료일보다 빠르다.
- 리뷰 이벤트의 대상 상품 ID가 실제 활성 상품으로 존재한다.
- 세일·신상품 이벤트의 카테고리는 실제 Firestore 카테고리 slug를 사용한다.
- 기존 한국어 카테고리 값은 manifest에서 `tops`, `bottoms`, `clothing`, `bags`, `shoes`, `accessories`, `sports` 중 실제 의미에 맞는 slug로 교체한다.
- `none` 자격과 `targetProducts`, `none` 보상과 `rewardCouponId`가 동시에 남지 않는다.
- 이미지 URL 또는 로컬 이미지 경로가 역할별로 존재한다.

### Firestore 적용 도구

도구는 `analyze`, `apply`, `verify`, `rollback` 단계를 분리한다.

1. `analyze`
   - 읽기 전용으로 현재 22개 문서와 상품·이미지 상태를 분석한다.
2. `apply`
   - 프로젝트 ID와 문서 수를 재확인한다.
   - 변경 전 22개 원본 문서를 로컬 백업 JSON으로 저장한다.
   - 이미지 업로드가 완료되고 manifest가 유효할 때만 32개 문서를 batch로 반영한다.
   - 이 단계에서는 `publicPolicyVerified: false`를 유지한다.
3. `verify`
   - 32개 문서의 필드와 이미지 접근성, 대상 상품 존재를 확인한다.
4. `rollback`
   - 기존 22개 문서를 백업 상태로 복원한다.
   - 신규 10개는 삭제하지 않고 `publicPolicyVerified: false`, `isActive: false`로 전환한다.
   - 신규 문서 삭제가 필요하면 파괴적 작업으로 분리해 별도 승인을 받는다.

Firestore batch는 32개 문서를 한 번에 처리해 일부 문서만 적용되는 상태를 방지한다. 이미지 업로드가 실패하면 Firestore 문서를 변경하지 않는다.

## 운영 공개 순서

운영 Firebase 프로젝트 `hebimall`은 로컬과 배포 사이트가 같은 Firestore를 읽는다. 따라서 데이터 공개와 코드 배포 순서를 다음과 같이 고정한다.

1. 로컬 코드와 manifest 작성
2. 테스트 및 Firestore Emulator 검증
3. 운영 Storage에 필요한 신규 이미지를 새 경로로 업로드
4. 운영 Firestore에 32개 문서를 `publicPolicyVerified: false`로 반영
5. 로컬 관리자·검증 도구에서 32개 문서 검사
6. 해비님에게 배포 승인 요청
7. 승인 후 이벤트 탭 코드와 이미지 경로 정책 배포
8. 배포된 운영 코드 확인
9. 32개 문서의 `publicPolicyVerified`를 한 batch로 `true` 전환
10. 운영 `/events/` 목록·상세·참여 상태 확인

배포 승인이 없으면 6단계에서 멈추며 운영 `/events/`는 기존처럼 공개 이벤트 0개 상태를 유지한다.

## 오류 처리와 복구

- manifest 검증 실패: 데이터나 Storage를 변경하지 않는다.
- 이미지 생성·업로드 실패: 해당 이벤트를 실패로 기록하고 Firestore 적용을 중단한다.
- Firestore batch 실패: 전체 batch가 반영되지 않은 것을 확인하고 종료한다.
- 검증 실패: 공개 값을 활성화하지 않는다.
- 배포 실패: Firestore는 검증 전 상태로 유지한다.
- 공개 후 회귀 발견: 32개 공개 값을 먼저 `false`로 되돌려 노출을 차단하고 원인을 수정한다.
- 기존 문서 복원이 필요하면 백업을 사용하고 신규 문서는 비공개·비활성 상태로 보존한다.

## 완료 기준

- 기존 이벤트 22개가 안전한 문구와 검증된 이미지로 재사용된다.
- 신규 이벤트 10개가 실제 상품과 현재 참여 계약에 맞게 추가된다.
- `/events/`에서 진행·예정 이벤트와 종료 이벤트가 분리된다.
- 종료 이벤트는 상세 조회가 가능하고 참여는 차단된다.
- 공개 이벤트 32개가 목록과 상세에서 정상 렌더링된다.
- 문구·이미지·상품·참여 조건 검증이 통과한다.
- 운영 반영 전 백업과 복구 경로가 확인된다.
- 타입체크, 린트, 관련 테스트, 빌드와 브라우저 QA가 통과한다.
