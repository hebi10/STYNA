# 관리자 상품 수정 Firebase 안전 모달 설계

## 배경

관리자 상품 목록에서 `수정`을 선택하면 Next.js 병렬·인터셉트 라우트의 정적 청크를 요청한다. 이 청크의 경로에는 `@`, `(`, `[`, `]` 등의 퍼센트 인코딩 문자가 포함된다. 현재 Firebase Hosting의 Cloud Run 기반 Functions v2 경로에서는 해당 URL 경로가 디코딩되어 청크를 찾지 못하고 `ChunkLoadError`가 발생한다.

직접 진입하는 `/admin/dashboard/products/[productId]/edit` 페이지와 Firestore 상품 데이터는 정상 동작한다. 따라서 상품 데이터나 수정 폼이 아니라, 목록에서 인터셉트 라우트를 여는 방식이 문제 범위다. Firebase App Hosting도 같은 Cloud Run URL 디코딩 제약을 문서화하고 있으므로, 호스팅 변경만으로는 해결하지 않는다.

## 목표

- 관리자 상품 목록에서 수정 폼을 현재와 같은 팝업 형태로 연다.
- Firebase Hosting/Functions v2에서 특수문자 인코딩 청크 경로를 요청하지 않는다.
- 새로고침과 URL 공유 후에도 특정 상품 수정 모달을 다시 열 수 있게 한다.
- 기존 직접 수정 URL은 전체 페이지 편집 화면으로 계속 유지한다.

## 범위 제외

- Firebase App Hosting 이전
- 상품 데이터 모델, 권한 정책, 저장 API 변경
- 기존 병렬·인터셉트 라우트 파일 삭제
- 수정 폼의 입력 항목이나 디자인 재구성

## URL 계약

상품 목록의 수정 상태는 다음 URL로 표현한다.

```
/admin/dashboard/products?edit=<productId>
```

- 목록의 `수정` 버튼은 위 쿼리 URL로 이동한다.
- `edit` 값이 유효하면 동일한 목록 화면 위에 모달을 연다.
- `edit` 값이 없으면 모달을 표시하지 않는다.
- 닫기, 취소, 저장 성공 후에는 `edit` 파라미터만 제거하고 다른 쿼리 파라미터가 있다면 유지한다.
- 직접 URL `/admin/dashboard/products/<productId>/edit`는 기존처럼 전체 페이지 편집 화면을 제공한다.

쿼리 문자열은 정적 청크의 파일 경로가 아니므로, Firebase의 경로 디코딩 제약을 피한다.

## 구성 및 데이터 흐름

1. 상품 목록 페이지는 URL의 `edit` 값을 읽는 전용 클라이언트 컴포넌트를 Suspense 경계 안에 렌더링한다.
2. 전용 컴포넌트는 `ProductProvider`의 `getProductById`로 상품을 조회한다. 기존 목록 데이터가 있으면 재사용하고, 없으면 기존 서비스 경로로 조회한다.
3. 조회가 완료되면 현재의 `EditProductForm`을 모달 안에서 재사용한다.
4. 저장은 기존 `updateProduct` 흐름을 그대로 사용한다. 저장 성공 시 Provider의 목록 상태와 캐시 무효화 동작을 보존한 뒤 `edit` 파라미터를 제거한다.
5. 모달 프레젠테이션은 기존 인터셉트 라우트의 스타일과 동작을 재사용 가능한 컴포넌트로 정리하거나, 그와 동일한 기존 스타일 규칙을 사용한다. 목록 진입 경로는 더 이상 인터셉트 라우트를 호출하지 않는다.

`useSearchParams`는 클라이언트 전용 경계에서 사용해 정적 페이지 빌드 시의 CSR bailout 오류를 방지한다.

## 모달 동작

- 배경 클릭, Escape, 닫기 버튼, 폼의 취소 버튼은 현재와 같은 미저장 변경 확인 흐름을 거친다.
- 모달이 열린 동안 본문 스크롤을 막고, 닫힐 때 원래 상태로 복원한다.
- `role="dialog"`, `aria-modal="true"`, 제목 연결 등 기존 접근성 속성을 유지한다.
- 상품 조회 중에는 로딩 상태를, 존재하지 않거나 조회에 실패하면 닫을 수 있는 오류 상태를 표시한다. 오류 상태가 전체 관리자 화면을 깨뜨리면 안 된다.
- URL의 상품 ID는 렌더링과 링크 생성 시 안전하게 인코딩·처리한다.

## 호환성 결정

| 진입 방식 | 수정 후 동작 |
| --- | --- |
| 상품 목록의 수정 버튼 | `?edit=<productId>` URL의 모달 |
| `?edit=<productId>` 직접 접속·새로고침 | 상품 목록 위의 모달 |
| 기존 `/products/<productId>/edit` 직접 접속 | 전체 페이지 편집 화면 |
| 기존 병렬·인터셉트 라우트 | 파일은 유지하되 목록에서 신규 진입을 만들지 않음 |

## 검증 계획

- 수정 버튼이 특수문자 인코딩 라우트가 아닌 `?edit=` URL을 만드는지 단위 또는 컴포넌트 테스트로 확인한다.
- 정상 상품, 잘못된 상품 ID, 조회 실패, 취소, 저장 성공의 모달 상태 전환을 테스트한다.
- 타입체크와 기존 린트/테스트 스크립트를 실행한다.
- 브라우저에서 관리자 목록의 수정 버튼을 눌러 팝업이 열리고 저장·취소·새로고침이 정상인지 확인한다.
- 기존 직접 수정 URL이 전체 페이지로 계속 열리는지 확인한다.
